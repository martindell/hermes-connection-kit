# Private integration source and migration gates — packaging does not install

This branch is stacked on the unmerged initial-kit branch. The reviewed implementation has since been installed and qualified on one host; this documentation/package branch makes no active service, installed tunnel client, research workflow or remote MCP configuration changes. That single-host baseline does not qualify a fresh-user installation. Independent review of the combined integration remains a migration gate for any different installation. No public release or license decision is implied.

## Contract

A caller submits a job exactly once using its existing MCP start tool. Only after a successful, unambiguous response containing `run_<32 lowercase hex>` does the caller invoke `hermes_register` with the returned ID, an exact configured project/repository/PR, a source correlation and a finite per-job absolute Unix UTC deadline (at least ten minutes ahead). Registration never starts or replays a task. If start is ambiguous, stop and reconcile with the existing provider status; do not start again. If registration is ambiguous, use `hermes_tracked` for that same ID; a 404 is not proof that a lost registration or start did not succeed. Never repeat the start for a registration failure. The adapter does not accept arbitrary commands, wildcard destinations or caller-provided URLs. The `mode=register` query parameter is ignored by the adapter and exists only for the Harpoon template schema.

The prepared `client-config.example.yaml` adds these two tools, pointed at a separately configured literal 127.0.0.1 control port (fictional example 18765). The authorization header is the same existing Hermes gateway API key already used by the tunnel, not a second credential. A static `systemd --user` control service receives the key through `LoadCredential` and `%d/gateway`, never the unit text or command line. It checks Bearer auth and routes; it binds only loopback. The private config's `gateway_credential_file` must be the retained owner-only key at the configured state directory. The key is shared by same-UID programs and does not create project isolation. The GitHub adapter uses existing `gh` auth and verifies the exact PR and publishing actor before a POST. The example config is fictional; a real owner-only `watchdog-config.json` is required alongside the reviewed source for the opt-in installation command. Pin/review its contents and control port; mutable owner-owned settings are not a security boundary against same-UID compromise.

After the managed tunnel has returned ready from its actual listener/PID, `connect` starts the control service and checks an authenticated `/health` response, enables the registry and starts a static timer. If any observer startup step fails, it stops only observer-owned units; if this connect started the tunnel, the existing cleanup also stops that tunnel. An already-ready tunnel remains untouched on observer failure, and the command does not claim all ready. A repeated connect is idempotent. A tick is a oneshot unit with a 44-second systemd start limit, scheduled every 60 seconds by a static timer (neither unit has boot enable). Its production path admits multiple operations while elapsed monotonic time plus the next operation's timeout estimate fits a 39-second admission budget (five seconds reserved for state and scheduler overhead), with a 64-operation ceiling. Worst-case per operation: known-run GET plus managed-unit check 9 seconds; paginated comment reconciliation plus PR/actor checks plus POST 26 seconds; acknowledgement-route comments 8 seconds. Starting phase rotates durably per invocation; separate run/event/ack cursors persist before outbound calls. Slow operations cannot consume every tick of another phase; fast operations use spare budget, including multiple observations and queued deliveries. The systemd limit kills an overrun rather than claiming a hard real-time guarantee against slow fsync, subprocess teardown, a trickling HTTP response or scheduler stalls; interrupted/ambiguous delivery is reconciled before any retry. At most 32 nonterminal runs may be registered; additional registrations fail without starting/replaying work. With 32 slow 9-second observations and a continuously busy outbox, a full observation cycle can take around 32 minute ticks (plus scheduler delay); this is not a one-minute SLA and an operator should register fewer slow jobs when quicker checks matter. Fast fictional 21-run observations and deliveries fit one tick; actual network and GitHub latency can reduce throughput. Event history remains durable and grows without automatic compaction, so monitor state size and queued-event age; capacity is not a promise of arbitrary notification lag. The 24-hour delivery window and five-attempt cap remain in force. There is no permanently running tick daemon. The control service runs while explicitly connected. `disconnect` stops the timer, drains/stops a tick and control service, then pauses registry delivery before stopping the tunnel. Registry and lifecycle locks have separate ownership; no registry lock is held while waiting for the tick to stop. A deliberate disconnect produces no connection-blocked event. Pending events and results stay owner-only and reconcile on an explicit reconnect. If the managed unit becomes inactive or its fragment identity changes without disconnect, the timer records one connection-blocked transition per tracked nonterminal run even when the independent gateway still reports running; each is queued for later delivery. The managed-unit check is read-only and does not prove listener readiness. It does not reconnect, stop, cancel or restart a Hermes run. If the host dies, notification stops; this is an accepted failure mode.

`watchdog.py` keeps a 0700 state directory and 0600 fsynced/atomically replaced registry/outbox. It only GETs a known run from the existing local gateway. HTTP 200 and `updated_at` are not job progress; overdue requires the registered deadline. Terminal status output stays in private result files, never GitHub. Events have deterministic project/run/kind/generation IDs. Before every PR POST it reads all paginated comments and reconciles only an exact marker from the configured actor; uncertain POST results are not blindly reposted. Five attempts and a 24-hour delivery window are the bound; exhausted events remain for read-only reconciliation. Delivery is not Work acknowledgement. Work must check the exact PR, marker, run ID and author, then obtain known-run status using its approved status tool and post only the exact correlated acknowledgement. The watcher records that acknowledgement separately; after 24 hours without it, it records local overdue state without reposting. Production webhook subscription must be restricted to the exact PR's issue_comment events; acknowledgement-only comments and delivery comments must not dispatch jobs. Test PR notification is a development channel, not a general event route.

## Review-gated migration/rollback procedure (not executed)

1. Before any approved live operation, compare installed code/config/unit bytes and current manager state against this reviewed SHA. Inspect the real source/config identities, owner and modes, current service/timer names, tunnel/target ports, gateway credential path, GitHub actor and exact PR route. Record SHA-256 and a private owner-only backup of installed `on-demand.py`, pinned client YAML, settings JSON, unit and retained credentials (credentials must not enter a repository/report). Back up the private registry if it already exists. Record `/readyz` and unit states. The settings file must be owner-owned 0600 with safe ancestor directories and no symlinks; a legacy looser mode requires a separately approved, reversible permission correction while stopped. The observer config must pin `managed_unit` and `managed_fragment` to the selected settings' exact user service name and unit path. An unexpected dirty or active service is a stop, not overwrite authority.
2. After separate explicit approval and review, only during a planned disconnected window, prepare the reviewed source and a 0600 host-local `watchdog-config.json` with exact allowlisted routes, existing Hermes gateway API key path and an available control port. Reconcile the changed client YAML and its SHA pin with the deployment-specific settings; do not copy the fictional example or swap the active YAML. Stage code/config/unit files byte-for-byte, compare hashes to the reviewed candidate and backups; use the approved `setup`/`install-observer` path only after collision checks. `install-observer` refuses an active tunnel, refuses changed owned artifacts and does not enable/start a unit. A staged upgrade of a pre-existing installed on-demand script needs a separately reviewed, byte-hashed replacement while stopped: the old kit's `setup` refuses changed artifacts by design, so do not use forced overwrite or pretend this branch has performed migration.
3. Validate staged units with `systemd-analyze verify` and native config parsing. Independently verify the installed script under `python3 -I` reads the pinned settings path passed in the unit, and the observer reads the correct private config, not the repository working directory. Only after approval connect explicitly, confirm tunnel readiness, authenticated control `/health`, timer activity, unchanged gateway process and scoped PR route. Execute one separately authorised harmless returned run, register its exact ID once, observe/reconcile delivery and Work acknowledgement. Do not treat offline tests as a live round trip.
4. Roll back only owned observer units/files and the reviewed installed script/YAML/settings from the private backup while stopped and with matching expected hashes. Stop timer/tick/control before any tunnel operation; retain the registry/outbox/results and credentials for reconciliation and audit. Compare restored file hashes, user-unit state, tunnel readiness if previously connected, and absence of unexpected unit enablement. No destructive uninstall, gateway restart, research automation change or job replay is part of rollback. If any hash, owner, state, route or status differs unexpectedly, stop for operator review rather than guessing.

## Offline verification

`TMPDIR="$HOME/mcp-private-tests" python3 -m unittest discover -s . -p 'test_*.py' -v` with a private directory under safe ancestors exercises lifecycle, watchdog, migration and package tests. Unit/service and loopback HTTP cases use fictional keys, routes and managers; no live daemon, provider, GitHub POST or real task is used. Native unit parsing and CI must be evaluated against the exact final revision. These checks do not qualify a fresh host's gateway authentication, external client template compatibility, systemd installation or Work's production webhook filter; the existing single-host baseline does not transfer automatically.
