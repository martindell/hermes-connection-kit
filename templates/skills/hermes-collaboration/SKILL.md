# Hermes collaboration — customisable skill template

Work plans and independently reviews; Hermes executes authorised work; a private GitHub issue stores durable instructions and receipts. Reuse an existing verified connection rather than installing a tunnel per thread. Read [the protocol](references/control-room-contract.md), [deployment template](references/deployment.md), and [new-project path](references/new-project.md) before relevant actions. This source is a template: replace owner, host, project, actor, route, conversation and command placeholders with verified local values before installing through your Work client's supported skill installation flow. Cloning this repository does not install or register a ChatGPT skill; verify that your Work product supports skills and the referenced webhook/MCP tools. Never treat a dated deployment note as current state or permission.

Choose the smallest workflow: for explanation/health, discover tools and read authorised known IDs only; never launch a test job just to prove availability. For an existing project, read its AGENTS.md, issue and all paginated receipts, known registration and callback scope; avoid duplicate installation or starts. For a new project/thread, resolve exact private repo, project key, substantive issue, permanent open doorbell PR, actor and owning conversation; reuse only verified matching infrastructure and qualify with one separately scoped harmless task. For a webhook, obey the saved exact project/run subscription, not another project's authority.

Discover current Hermes MCP/GitHub/Automations capabilities and `list_targets` schemas; don't hard-code write operation tokens. Read `hermes_status` for known accepted IDs and `hermes_tracked` for known registered IDs. Tool discovery is not host reachability. If disconnected, supply the verified host `status`/`connect` command from the customised deployment reference; the disconnected MCP cannot repair itself. Do not regenerate credentials, request pasted secrets, or inspect unrelated jobs. Preserve another conversation's callback ownership; shared tunnel credentials are not project isolation. Configure one persistent webhook for exact PR comments only, after checking ownership/duplicates; do not substitute a scheduled poll or manually trigger a webhook as roundtrip proof.

For project setup, record [manifest](references/project-manifest.md) with scope and source authority; keep substantive results on issue and event/ack comments on PR. Inspect private config, units, ownership, lock, active jobs and registered IDs before proposing an additive route. Back up and review exact diffs/hashes; adding a route can require a scoped control-service restart, which needs distinct authorisation. Never interrupt shared services merely to set up a new thread.

Dispatch: read all issue comments for duplicate intent/accepted start/active result. Write one bounded unmarked source instruction with exclusions and return issue. Invoke discovered `hermes_start` once; retain unambiguous accepted run ID and disposition. A timeout/lost/malformed response is UNKNOWN, not authority to start again. Record source, run, correlation, project/repo/PR and finite UTC deadline in issue. For callback, register the exact accepted ID once via discovered `hermes_register`, with an exact route and deadline at least ten minutes ahead for this baseline. Read back `hermes_tracked`; registration does not start a task. Reconcile ambiguous registration or receipt writes without replay. Background follow-up requires verified route, subscription and registration, not repeated foreground polling.

Review: inspect exact SHA, changed files, tests and handoff independently. A worker PASS or HTTP200 is not proof. For a new route, one authorised no-tools fixed-output task is enough to test terminal output, actual timer/PR event, correct Work conversation, exact marker-only ack, issue ledger and later observer reconciliation separately. Test overdue/duplicate/pause in disposable fixtures; live tests require bounded separate authority and restoration of test-owned state. Deadline passage is not proof of a stall. Don't cancel jobs, pause observer or alter shared services on callback. Keep persistent subscription enabled after no-op/duplicates/failures; no minute-latency SLA or host-death survival is promised.

End-of-session reminder: on finishing foreground work or when the user stops, remind once, conditionally if other threads' use is unknown: “If no other threads need Hermes, remember to disconnect the shared tunnel.” Check known pending work; if callbacks remain, explain why connection should stay open. Supply the verified host command with `disconnect` from the customised deployment reference when first relevant or requested. Disconnect affects all threads, pauses notifications, retains credentials/state and does not cancel accepted jobs. Never disconnect automatically, uninstall or disable the persistent subscription. This is an in-conversation reminder, not tab-close detection or a scheduled automation.
